Deep Dive: Breaking and Securing the npm Supply Chain Against Dependency Confusion

Posted: 2026-06-03 | Categories: Security, AppSec

In modern software development, we rely heavily on the convenience of third-party open-source libraries. However, this convenience introduces severe risks to the software supply chain. A prominent threat in this landscape is Dependency Confusion (namespace shadowing)—an attack that tricks automated systems into pulling malicious public code instead of internal private packages to achieve Remote Code Execution (RCE).

Technical Aspects

The Default Resolution Algorithm

To understand why dependency confusion happens, look at how the npm client behaves when configured with a unified registry proxy (a Virtual Repository in JFrog Artifactory or a Combined Group in Sonatype Nexus). A virtual repository aggregates multiple repositories into a single endpoint, typically combining local private repositories and a remote proxy to the public npm registry.

When a developer runs npm install, the npm client queries this virtual endpoint for a package metadata manifest (the packument). If a package exists in both the local private repository and the remote public proxy, Artifactory may merge metadata. The npm client then selects the highest semantic version. In short:

$$\text{Selected Version} = \max(\text{Versions Available from Local} \cup \text{Versions Available from Remote})$$

Because npm prefers the highest SemVer number, an attacker publishing a high-version package (for example, v99.9.9) on the public registry can cause the virtual repository to serve the malicious public package over an internal v1.0.0 asset.

The Execution Mechanism

The attack often escalates via npm lifecycle scripts. An attacker can publish a package with malicious install hooks, for example:

{
  "name": "internal-payment-gateway",
  "version": "99.9.9",
  "scripts": {
    "preinstall": "node ./malicious-telemetry.js"
  }
}

The moment npm install extracts such a tarball, the node runtime executes ./malicious-telemetry.js with the privileges of the running shell. And exfiltrate secrets (like AWS_ACCESS_KEY_ID, NPM_TOKEN, or GITHUB_TOKEN), read local files, or open reverse shells.

Defense

Why Scoped Packages Defend Against Dependency Confusion

Moving from unscoped names (internal-payment-gateway) to scoped packages (@corporate-scope/payment-gateway) is a primary mitigation. Scopes provide:

  • Global uniqueness: Registering your scope on the public registry prevents outsiders from publishing packages using that prefix.
  • Deterministic routing: Client-side configuration in .npmrc can pin a scope to an internal registry, for example:
# Default to public registry for open-source assets
registry=https://npmjs.org

# Explicitly isolate the corporate scope to internal registry
@corporate-scope:registry=https://internal.corp

How Attackers Bypass Scopes

1. "Internal-only" scope not reserved publicly

If teams create an internal scope but never reserve it on the public registry, an attacker who discovers the scope name can register it publicly and publish malicious high-version packages. This becomes dangerous if a CI/CD runner or developer machine falls back to the public registry.

2. Virtual repository overrides

If scoped traffic is routed through an Artifactory virtual repository that allows remote lookups, the virtual repo may fetch an attacker's high-version package from the public registry and return it instead of the local package.

[Developer Machine] ──► Requests: @my-secret-org/auth
                              │
                    [Artifactory Virtual Repo]
                              ├── Local Private Index (Has v1.0.0)
                              └── Remote Proxy to npmjs.org (Attacker uploaded v99.9.9)

3. Transitive dependency injection

A scoped package may depend on an unscoped internal package (for example, utility-logger). If that unscoped name is unreserved on the public registry, attackers can publish it and compromise the dependency chain.

Defense in Depth

Implement multiple layers of controls:

Layer 1: Repository-level routing & exclude patterns

Enforce protections on artifact servers. In Artifactory or Nexus, set repository exclude patterns or routing rules to prevent public lookups for corporate scopes (for example, exclude @corporate-scope/** from remote proxy).

Layer 2: Namespace reservation

Reserve and register corporate scopes and critical unscoped package names on the public npm registry (even as empty placeholders) to prevent squatting.

Layer 3: Deterministic lockfiles

Commit lockfiles (package-lock.json, yarn.lock, pnpm-lock.yaml) and use npm ci in CI to ensure exact versions and integrity hashes are enforced.

Layer 4: Execution isolation

Run installs with scripts disabled where appropriate:

npm ci --ignore-scripts

Using these controls together—repository routing, namespace reservation, deterministic lockfiles, and execution isolation—significantly reduces the attack surface for dependency confusion.
