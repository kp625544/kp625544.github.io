Deep Dive: The OAuth Identity Paradox — Why Verified Emails Are Not Proof of Employment

Posted: 2026-06-06 | Categories: Security, IAM

Modern SaaS applications rely heavily on OAuth. Users can sign in using GitHub, Google, Microsoft, GitLab, LinkedIn, and dozens of other identity providers with a single click.

While OAuth simplifies authentication, many systems accidentally treat identity attributes as authorization signals. The most common example is the email address.

This creates a subtle trust problem: 


Does a verified email prove current ownership?

Does current ownership prove organizational affiliation?

Does organizational affiliation prove authorization?

The answer to all three questions is different.

Understanding the Three Trust Levels

Before discussing OAuth vulnerabilities, we need to distinguish between three separate identity claims that are often confused.

Level 1: Historical Verification

Most OAuth providers operate using historical verification. 


2023:
alice@company.com verified

2026:
email_verified = true

The provider is only asserting: 


User completed our email verification process.

It is NOT asserting: 


User currently controls mailbox.

User still works at company.

Level 2: Periodic Verification

Some platforms periodically revalidate ownership. 


2023:
alice@company.com verified

2024:
reverify

2025:
reverify

The resulting trust statement becomes: 


User recently demonstrated mailbox ownership.

This is stronger than historical verification but still does not prove employment.

Level 3: Live Enterprise Identity

Enterprise Identity Providers work differently. 


HR System
    ↓
Google Workspace / Entra / Okta
    ↓
SAML / SCIM
    ↓
SaaS Platform

Here the claim becomes: 


The company currently asserts this user exists.

This is significantly stronger than email verification.

The Employee Offboarding Problem

Consider a company called ABC.

Every employee receives: 


alice@abc.com

through Google Workspace.

The company uses a SaaS platform that supports: 


Login with Google

Login with GitHub

Alice signs into the SaaS using Google. 


Google OAuth
    ↓
alice@abc.com
    ↓
SaaS Account

Later she adds the same work email to GitHub: 


GitHub Account
    ↓
Verified Email:
alice@abc.com

Everything works as expected.

What Happens When Alice Leaves?

ABC disables: 


alice@abc.com

inside Google Workspace.

Now: 


Google Login
    ↓
Fails

However: 


GitHub Login
    ↓
Succeeds

because the GitHub account still exists.

Most people immediately conclude:

This is a vulnerability.

But is it?

Authentication vs Authorization

OAuth only answers: 


Who are you?

It does not answer: 


Should you have access?

This distinction is critical.

GitHub can legitimately claim: 


Alice verified this email.

GitHub cannot claim: 


Alice still works at ABC.

Those are completely different assertions.

The Dangerous Shortcut

Many SaaS applications accidentally perform authorization using email addresses. 


if email.endswith("@abc.com"):
    grant_access()

This appears reasonable.

However, the authorization decision is now based on: 


Historical Email Verification

instead of: 


Current Organizational Membership

The trust boundary has shifted without anyone noticing.

Why SSO Alone Does Not Solve This

A common recommendation is:

Enforce SSO.

While useful, SSO alone does not solve the problem. 


Google OAuth
GitHub OAuth

Both remain valid identity providers.

After offboarding: 


Google Login
    ↓
Blocked

GitHub Login
    ↓
Allowed

The existence of SSO does not automatically invalidate other identity providers.

The SaaS must decide which provider is authoritative for authorization decisions.

The OAuth Identity Paradox

The most interesting observation is that email verification is often treated as a much stronger signal than it actually is.

Many systems implicitly convert: 


User verified email once.

into: 


User currently owns mailbox.

and then further into: 


User currently belongs to organization.

Each conversion introduces additional assumptions.

Eventually, authorization decisions depend on claims that were never actually made by the identity provider.

Conclusion

OAuth providers answer authentication questions.

Organizations answer employment questions.

SaaS platforms answer authorization questions.

Problems emerge when these responsibilities become mixed together.

The most dangerous OAuth issues rarely involve cryptography, token validation, or protocol implementation flaws. Instead, they emerge when one system assumes another system is making a stronger security assertion than it actually is.

The result is an identity paradox: 


Authentication proves identity.

Authorization requires trust.

Email addresses sit somewhere in the middle.

And that gray area is where some of the most interesting OAuth security discussions begin.
